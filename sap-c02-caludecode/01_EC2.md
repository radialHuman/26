# 01 — Amazon EC2 (Elastic Compute Cloud) — Exhaustive Deep-Dive

## 1. What Problem EC2 Solves

### The World Before EC2

Imagine you want to launch a website or run an application. Before EC2 (before 2006), here is what you had to do:

1. **Buy physical servers** — You had to purchase actual computer hardware. A single enterprise-grade server cost $5,000–$50,000+.
2. **Find a place to put them** — You either built your own data center (millions of dollars) or rented space in a colocation facility ($500–$5,000/month per rack).
3. **Wait weeks or months** — Ordering, shipping, racking, cabling, installing an operating system, configuring networking — this took 4–12 weeks minimum.
4. **Over-provision for peak** — If your website got 100 visitors/day normally but 10,000 on Black Friday, you had to buy enough servers for 10,000 visitors and let them sit idle the rest of the year. You paid for 100% of the hardware 100% of the time, even if you used 5% of its capacity.
5. **Handle failures yourself** — If a hard drive died at 3 AM, someone had to physically go replace it.
6. **Guess the future** — You had to predict your computing needs 1–3 years in advance because that's how long hardware purchasing cycles took.

### What EC2 Changed

EC2 lets you rent virtual computers (called **instances**) from Amazon's massive data centers. The key breakthroughs:

| Before EC2 | After EC2 |
|---|---|
| Buy servers ($5K–$50K each) | Rent by the second (starting at $0.0058/hour) |
| Wait 4–12 weeks | Launch in seconds |
| Over-provision for peak | Scale up/down on demand |
| Pay for idle capacity | Pay only for what you use |
| Handle hardware failures | AWS replaces failed hardware automatically |
| Guess future needs | Adjust in real-time |
| Upfront capital expense (CapEx) | Operational expense (OpEx) |

### Real-World Example

**Netflix** used to run its own data centers. In 2008, a major database corruption took down DVD shipments for 3 days. They decided to move to AWS. Today, Netflix runs thousands of EC2 instances that scale up during evening viewing hours (peak) and scale down overnight. They pay only for what they use, and if a single instance fails, traffic automatically routes to healthy instances. They couldn't have built their global streaming service without EC2's elasticity.

**Airbnb** started on a single EC2 instance. As they grew from 0 to millions of users, they simply launched more instances. No hardware purchases, no data center buildout — they scaled from a startup idea to a $75B company on rented compute.

## 3. When to Use EC2

### 10+ Use Cases (When EC2 is the Right Choice)

1. **Web Application Hosting** — Running web servers (Apache, Nginx, IIS) that serve your website or web application
2. **Application Servers** — Running backend logic (Java, .NET, Python apps) that process requests
3. **Batch Processing** — Running large computational jobs (video encoding, data processing, scientific simulations) where you need sustained compute
4. **Database Hosting (Self-Managed)** — When you need a database engine or version that RDS doesn't support (e.g., specific Oracle configurations, custom PostgreSQL extensions)
5. **Development and Testing** — Spin up instances quickly for dev/test environments, tear them down when done
6. **High-Performance Computing (HPC)** — Scientific simulations, weather modeling, genomics using cluster placement groups and enhanced networking
7. **Machine Learning Training** — Using GPU instances (P4, P5) for training deep learning models
8. **Gaming Servers** — Hosting multiplayer game servers requiring low latency and dedicated compute
9. **Legacy Application Migration** — "Lift and shift" of on-premises applications that can't easily be containerized or made serverless
10. **Bastion Hosts / Jump Boxes** — A secure entry point into your private network for SSH/RDP access
11. **CI/CD Build Servers** — Running Jenkins, GitLab runners, or other build tools
12. **Rendering** — 3D rendering, video processing using GPU-equipped instances

### 5+ Anti-Patterns (When NOT to Use EC2)

1. **Short-lived, event-driven functions** → Use **Lambda** instead. If your code runs for <15 minutes and responds to events (API calls, file uploads, queue messages), Lambda is cheaper and simpler — no server management needed.
2. **Static websites** → Use **S3 + CloudFront**. No compute instance is needed for HTML/CSS/JS files.
3. **Containerized microservices at scale** → Use **ECS/EKS with Fargate**. If you're running containers, Fargate removes the need to manage the underlying EC2 instances.
4. **Simple web applications with predictable traffic** → Consider **Lightsail** or **App Runner**. These are simplified compute services that handle most of the configuration for you.
5. **Highly variable, unpredictable workloads with sub-second bursts** → **Lambda** handles this more cost-effectively, as you don't pay for idle time between bursts.
6. **Running a managed database** → Use **RDS** or **Aurora**. Running your own database on EC2 means YOU handle backups, patching, failover, replication — RDS does all this for you.

## 4. How EC2 Differs from Similar Services

### EC2 vs Lambda

| Feature | EC2 | Lambda |
|---|---|---|
| Management | You manage the OS, patching, scaling | Fully managed, no servers to manage |
| Billing | Per-second (minimum 60 seconds) | Per-millisecond of execution |
| Max execution time | Unlimited | 15 minutes |
| Scaling | Manual or Auto Scaling (takes minutes) | Automatic, instant (milliseconds) |
| State | Stateful (persists between requests) | Stateless (no persistent local state) |
| OS Access | Full root/admin access | No OS access |
| Max memory | Up to 24 TB (u-24tb1.metal) | Up to 10 GB |
| Use case | Long-running apps, legacy workloads | Event-driven, short tasks |
| Cold start | Minutes to launch | Milliseconds to seconds |
| Cost for steady workloads | Cheaper (Reserved/Savings Plans) | More expensive for always-running |
| Cost for sporadic workloads | Expensive (paying while idle) | Cheaper (pay only when running) |

### EC2 vs ECS (Elastic Container Service)

| Feature | EC2 (standalone) | ECS on EC2 | ECS on Fargate |
|---|---|---|---|
| What you manage | Full OS + application | EC2 instances + containers | Just containers |
| Deployment unit | AMI/instance | Docker container | Docker container |
| Scaling unit | Entire instance | Container (task) | Container (task) |
| Resource efficiency | One app per instance (typically) | Multiple containers per instance | One task = dedicated compute |
| OS Access | Full | Full (on EC2) | None |
| Networking | Instance networking | awsvpc or bridge mode | awsvpc mode |
| Best for | Monoliths, legacy apps | Container workloads with specific EC2 needs | Container workloads, hands-off |

### EC2 vs Lightsail

| Feature | EC2 | Lightsail |
|---|---|---|
| Complexity | Hundreds of options | Simple, pre-configured |
| Pricing | Pay-per-use, complex | Fixed monthly (starts at $3.50/month) |
| Networking | Full VPC control | Simplified networking |
| Instance types | 500+ types | ~10 plans |
| Auto Scaling | Yes | No |
| Target audience | Engineers building complex architectures | Developers wanting simple deployments |
| Ecosystem integration | Full AWS integration | Limited AWS integration |
| Best for | Production enterprise workloads | Simple websites, WordPress, dev environments |

## 5. Underlying Mechanism — How EC2 Actually Works

### The Nitro System

Since 2017, most EC2 instances run on the **Nitro System**, Amazon's custom-built hardware and software platform. Understanding Nitro helps you understand why EC2 is fast and secure:

1. **Nitro Cards** — Custom hardware that handles networking, storage (EBS), and instance management. By offloading these to dedicated hardware, the main CPU is 100% available for YOUR workload (older instances lost 10–30% of CPU to hypervisor overhead).

2. **Nitro Hypervisor** — An extremely lightweight hypervisor (think of it as a thin software layer that lets multiple virtual machines run on one physical server). It's so minimal that it provides bare-metal-like performance.

3. **Nitro Security Chip** — Hardware-based security that protects the system firmware and prevents unauthorized access, even by Amazon employees.

### How an Instance Launches (The Request Flow)

Here's what happens when you click "Launch Instance":

```
You (Console/CLI/SDK)
    → AWS API (ec2.amazonaws.com)
        → EC2 Control Plane validates your request
            → Checks: Do you have permission (IAM)? Is your VPC/subnet valid? Is the AMI available?
                → Placement Engine finds a physical host
                    → Host has capacity? Right instance family? Right AZ?
                        → Nitro Controller on the physical host:
                            1. Creates virtual CPU, memory allocation
                            2. Attaches EBS volumes via Nitro Card
                            3. Configures networking via Nitro Card
                            4. Boots the AMI (operating system image)
                            5. Runs User Data script (if provided)
                            6. Instance state: "running"
                                → You can now SSH/RDP into it
```

### Placement Groups

Placement groups control HOW instances are physically placed on hardware. There are three types:

| Type | What It Does | Use Case | Exam Tip |
|---|---|---|---|
| **Cluster** | Packs instances close together on same rack | HPC, low-latency networking (10 Gbps between instances) | Single AZ only, best for network-intensive |
| **Spread** | Places each instance on different physical hardware | Critical instances that must not fail together | Max 7 instances per AZ per group |
| **Partition** | Groups instances into partitions on separate racks | Big data (HDFS, HBase, Cassandra) | Up to 7 partitions per AZ |

### Tenancy Models

| Model | What It Means | Cost | Use Case |
|---|---|---|---|
| **Shared (default)** | Your instance shares a physical host with other AWS customers' instances | Cheapest | Most workloads |
| **Dedicated Instance** | Your instance runs on hardware dedicated to your account (but may share with YOUR other instances) | ~2× cost | Compliance requirements |
| **Dedicated Host** | You get an entire physical server | Most expensive | License compliance (e.g., Oracle per-socket licensing), regulatory requirements |

## 6. Basic Components and Working

### Instance Types — The Naming Convention

EC2 instance names follow a pattern: **[Family][Generation].[Size]**

Example: `m5.xlarge`
- **m** = Family (General Purpose)
- **5** = Generation (5th generation)
- **xlarge** = Size (4 vCPUs, 16 GB RAM)

### Instance Families

| Family | Letter | Optimized For | Example Use Case | Example Instance |
|---|---|---|---|---|
| **General Purpose** | M, T, A | Balanced compute/memory/network | Web servers, small databases | m5.xlarge, t3.medium |
| **Compute Optimized** | C | High-performance processors | Batch processing, gaming, ML inference | c5.2xlarge |
| **Memory Optimized** | R, X, z | Large amounts of RAM | In-memory databases, real-time processing | r5.4xlarge, x1e.32xlarge |
| **Storage Optimized** | I, D, H | High sequential read/write to local storage | Data warehousing, distributed filesystems | i3.xlarge, d2.8xlarge |
| **Accelerated Computing** | P, G, Inf, Trn | GPUs, FPGAs, custom chips | ML training/inference, 3D rendering | p4d.24xlarge, g5.xlarge |

### T-Series: Burstable Instances (Exam Favorite!)

T-series instances (t3, t3a, t4g) are special:
- They have a **baseline CPU performance** (e.g., t3.medium baseline = 20% CPU)
- When you use LESS than the baseline, you earn **CPU Credits**
- When you need MORE than the baseline, you spend credits to "burst"
- **Unlimited mode** (default for t3): If you run out of credits, you're charged extra per-vCPU-hour instead of being throttled
- **Standard mode**: When credits run out, performance is capped at baseline

**Exam Trap**: "An application on a t3.micro is experiencing slow performance in the afternoons" → The instance is running out of CPU credits. Solution: Switch to unlimited mode, or upgrade to a larger/non-burstable instance.

### AMIs (Amazon Machine Images)

An AMI is a template that contains:
- The operating system (Linux, Windows, macOS)
- Pre-installed software
- Configuration settings
- Block device mapping (what storage to attach)

Types of AMIs:
- **AWS-provided**: Amazon Linux 2, Ubuntu, Windows Server, etc.
- **AWS Marketplace**: Third-party software pre-installed (e.g., Wordpress, custom security appliances)
- **Community AMIs**: Public AMIs shared by other users (use with caution!)
- **Custom AMIs**: You create these from your configured instances

**Exam Critical**: AMIs are **regional**. To use an AMI in another region, you must **copy** it to that region. AMIs can be shared across accounts.

### EBS Volumes (Elastic Block Store)

EBS provides persistent block storage for EC2 instances. Think of it as a virtual hard drive.

| Volume Type | IOPS | Throughput | Use Case | Exam Note |
|---|---|---|---|---|
| **gp3** (General Purpose SSD) | 3,000 baseline, up to 16,000 | 125 MB/s baseline, up to 1,000 MB/s | Most workloads, boot volumes | Default choice, IOPS/throughput independently configurable |
| **gp2** (General Purpose SSD) | 3 IOPS/GB, burst to 3,000 | Up to 250 MB/s | Legacy default | IOPS tied to volume size (larger volume = more IOPS) |
| **io2 Block Express** | Up to 256,000 | Up to 4,000 MB/s | Critical databases, highest performance | Most expensive, for sub-millisecond latency |
| **io1** | Up to 64,000 | Up to 1,000 MB/s | Databases needing guaranteed IOPS | Supports Multi-Attach (attach to multiple instances) |
| **st1** (Throughput Optimized HDD) | Up to 500 | Up to 500 MB/s | Big data, data warehouses, log processing | Cannot be boot volume |
| **sc1** (Cold HDD) | Up to 250 | Up to 250 MB/s | Infrequent access, lowest cost | Cannot be boot volume |

**Exam Critical**:
- EBS volumes are **AZ-locked** — an EBS volume in us-east-1a can only attach to instances in us-east-1a
- To move EBS data across AZs: snapshot → restore in new AZ
- To move across regions: snapshot → copy snapshot to new region → restore
- EBS snapshots are **incremental** (only changed blocks are saved)
- Root volumes are deleted by default when instance terminates (configurable)

### Instance Store (Ephemeral Storage)

- Physically attached to the host (not network-attached like EBS)
- **Extremely fast** (millions of IOPS for NVMe-based)
- **Data is LOST** when instance stops, terminates, or the underlying host fails
- Cannot be detached and reattached
- **Use case**: Temporary data, caches, buffers, scratch data

**Exam Trap**: "Need highest possible IOPS for temporary data" → Instance Store, NOT EBS

### ENI (Elastic Network Interface)

A virtual network card attached to your instance. Each instance has at least one ENI (primary). You can attach additional ENIs.

Key attributes:
- Private IPv4 address (from subnet CIDR)
- Elastic IP address (static public IP)
- MAC address
- One or more security groups
- Source/destination check flag

**Exam Use Case**: Attach a secondary ENI from a different subnet to create a management network interface. ENIs persist independently from the instance — you can move them between instances for failover.

### Security Groups (Exam Critical!)

Security groups are **virtual firewalls** that control traffic to/from instances.

Key characteristics:
- **Stateful** — If you allow inbound traffic, the response is automatically allowed outbound (and vice versa)
- **Allow rules only** — You can only specify ALLOW rules, not DENY. Everything not explicitly allowed is denied.
- **Instance-level** — Attached to ENIs (which are on instances)
- **Can reference other security groups** — Instead of IP addresses, you can say "allow traffic from instances in security group X"
- Default: All outbound allowed, all inbound denied

### User Data

A script that runs automatically when an instance first launches. Used to:
- Install software (`yum install httpd -y`)
- Configure the application
- Download code from S3
- Register with a configuration management system

Runs as root. Only runs on **first boot** by default (not on stop/start).

### IMDS — Instance Metadata Service (v1 vs v2)

Every EC2 instance can query its own metadata from a special URL: `http://169.254.169.254/latest/meta-data/`

This provides: instance ID, AMI ID, public IP, IAM role credentials, etc.

| Feature | IMDSv1 | IMDSv2 (Recommended) |
|---|---|---|
| How to access | Simple HTTP GET | Requires a PUT to get a token, then use token in GET |
| Security | Vulnerable to SSRF attacks | Protected against SSRF (requires token) |
| Recommendation | Legacy, disable if possible | Always use v2 |

**Exam Tip**: If a question mentions "an attacker accessed IAM credentials from the metadata service via SSRF" → The answer involves enabling IMDSv2 and/or disabling IMDSv1.

## 7. Cost — Detailed Breakdown

### Pricing Models

#### 1. On-Demand

- Pay by the second (Linux) or by the hour (Windows)
- No commitment, no upfront cost
- Most expensive per-hour rate

**Example**: m5.xlarge in us-east-1 ≈ $0.192/hour
- Running 24/7 for a month: $0.192 × 24 × 30 = **$138.24/month**

#### 2. Reserved Instances (RIs)

Commit to 1 or 3 years for significant discounts.

| Payment Option | 1-Year Discount | 3-Year Discount |
|---|---|---|
| All Upfront | ~40% off On-Demand | ~60% off On-Demand |
| Partial Upfront | ~35% off | ~55% off |
| No Upfront | ~30% off | ~50% off |

**Two Types**:
- **Standard RI**: Highest discount. Can change AZ, instance size (within family), networking type. CANNOT change instance family or OS.
- **Convertible RI**: Lower discount (~33% for 1-year). CAN change instance family, OS, tenancy. More flexible.

**Example Calculation**:
- m5.xlarge On-Demand: $138.24/month = $1,658.88/year
- m5.xlarge 1-year Standard RI, All Upfront: ~$996/year (40% savings = **$663 saved**)
- m5.xlarge 3-year Standard RI, All Upfront: ~$663/year (60% savings = **$996 saved per year**)

#### 3. Savings Plans

A newer, more flexible alternative to RIs:
- **Compute Savings Plan**: Commit to a $/hour spend. Applies to ANY EC2 instance, Lambda, and Fargate. Up to 66% off. Most flexible.
- **EC2 Instance Savings Plan**: Commit to a specific instance family in a region. Up to 72% off. Less flexible but deeper discount.

#### 4. Spot Instances

- Use spare EC2 capacity at up to **90% discount**
- AWS can reclaim (interrupt) your instance with a **2-minute warning**
- Best for: batch jobs, data analysis, CI/CD, fault-tolerant workloads
- NOT for: databases, critical web servers, anything that can't handle interruption

**Example**: m5.xlarge On-Demand: $0.192/hour → Spot: ~$0.04/hour (80% off)

**Spot Fleet**: A collection of Spot Instances (and optionally On-Demand) that maintains your target capacity. Strategies:
- **lowestPrice**: Launches from the cheapest pool
- **diversified**: Spreads across multiple pools (more resilient to interruption)
- **capacityOptimized**: Launches from pools with most available capacity (least likely to be interrupted)

#### 5. Dedicated Hosts

- An entire physical server dedicated to you
- Billed per host (not per instance)
- Required for: Bring Your Own License (BYOL) for software like Windows Server, SQL Server, Oracle that license per-socket or per-core
- m5.xlarge Dedicated Host: ~$1.834/hour (can run multiple instances on it)

### Cost Optimization Strategies

1. **Right-size instances**: Use CloudWatch CPU/memory metrics. If average CPU < 40%, downsize.
2. **Use Graviton (Arm) instances**: m6g/c6g/r6g are ~20% cheaper with 40% better price-performance than x86 equivalents.
3. **Mix pricing models**: RIs for baseline, Spot for variable, On-Demand for peaks.
4. **Schedule non-production**: Stop dev/test instances nights and weekends (save ~65%).
5. **Use Auto Scaling**: Scale down during low-traffic periods.
6. **Use Spot for fault-tolerant workloads**: Batch processing, CI/CD, rendering.
7. **Review regularly**: Use AWS Cost Explorer and Compute Optimizer.

## 8. Pros and Cons

### Pros

1. **Massive variety** — 500+ instance types covering every workload imaginable
2. **Global availability** — Available in 30+ regions, 90+ Availability Zones
3. **Seconds to launch** — Go from zero to running server in under a minute
4. **Elastic scaling** — Scale from 1 to thousands of instances on demand
5. **Multiple pricing models** — On-Demand, Reserved, Spot, Savings Plans, Dedicated — optimize cost for any usage pattern
6. **Spot Instances** — Up to 90% discount for fault-tolerant workloads
7. **Deep ecosystem integration** — Works seamlessly with VPC, ELB, Auto Scaling, CloudWatch, IAM, S3, RDS, and every other AWS service
8. **Full OS control** — Root/admin access, install any software, configure anything
9. **Security** — Nitro Security Chip, encrypted EBS, security groups, VPC isolation, IAM roles
10. **Graviton processors** — 40% better price-performance with Arm-based instances
11. **Bare metal options** — Run directly on hardware when you need it (licensing, specialized workloads)
12. **Quick iteration** — Launch, test, destroy — minimal cost for experimentation

### Cons

1. **Management overhead** — You must patch the OS, manage security updates, configure monitoring
2. **Capacity planning still needed** — Even with Auto Scaling, you need to configure scaling policies
3. **Cost can spiral** — Forgotten instances, over-provisioned resources, lack of monitoring = surprise bills
4. **Spot Instance interruptions** — 2-minute warning isn't always enough for complex workloads
5. **AMI management complexity** — Custom AMIs need patching, versioning, cross-region copying
6. **Instance limits** — Default limits per region (e.g., 20 On-Demand per instance family) require increase requests
7. **AZ failure risk** — If you're only in one AZ and it goes down, your instances go down (must architect for Multi-AZ)
8. **Noisy neighbor** (shared tenancy) — Other customers on the same physical host can occasionally impact performance (rare with Nitro, but possible)
9. **Not serverless** — You pay while instances run, even if they're idle
10. **Configuration complexity** — Hundreds of options means more opportunity for misconfiguration

## 9. SAP-C02 Exam Questions (15+ Scenarios)

### Question 1 — Spot Instance Strategy
**Scenario**: A company runs a video transcoding pipeline that processes uploaded videos. Jobs take 5–20 minutes each and can be restarted if interrupted. The company wants to minimize costs. What should they use?

**Answer**: **EC2 Spot Instances with a Spot Fleet using capacityOptimized strategy**

**Why correct**: The workload is fault-tolerant (can restart), short-running (5–20 min), and batch-oriented — perfect for Spot (up to 90% savings). capacityOptimized minimizes interruptions.

**Why others wrong**:
- On-Demand: Works but costs 5–10× more with no benefit for this use case
- Reserved Instances: Overkill for batch jobs — you'd be paying for reserved capacity 24/7 for a variable workload
- Lambda: 15-minute max execution time. Some jobs are 20 minutes, so Lambda can't handle them all.

---

### Question 2 — T-Series CPU Credits
**Scenario**: A development team's t3.micro instance becomes unresponsive every afternoon. Morning performance is fine. What is the MOST LIKELY cause?

**Answer**: **The instance is exhausting its CPU credits due to sustained usage**

**Why correct**: T-series instances burst above baseline using credits. Morning builds credits, afternoon heavy use depletes them.

**Fix**: Enable T3 Unlimited mode, or upgrade to a non-burstable instance (m5, c5).

---

### Question 3 — Placement Groups
**Scenario**: A financial trading application requires the lowest possible network latency between 20 EC2 instances. Which placement group strategy should be used?

**Answer**: **Cluster Placement Group**

**Why correct**: Cluster places instances on the same rack/nearby racks in a single AZ, enabling 10–25 Gbps network throughput with lowest latency.

**Why others wrong**:
- Spread: Separates instances across hardware (opposite of what we need — higher latency)
- Partition: Designed for distributed systems like Hadoop, not for lowest latency between all nodes

---

### Question 4 — Reserved vs Savings Plans
**Scenario**: A company has a steady workload running m5.xlarge instances but plans to migrate to Graviton-based m6g.xlarge in 6 months. They want cost savings. What should they choose?

**Answer**: **Compute Savings Plan (1-year)**

**Why correct**: Compute Savings Plans apply to ANY instance family, so when they switch from m5 to m6g, the discount still applies. A Standard RI on m5 would NOT transfer to m6g.

**Why others wrong**:
- Standard RI: Locked to m5 family (can't change to m6g)
- Convertible RI: CAN change family, but lower discount than Compute Savings Plan and more complex to manage
- EC2 Instance Savings Plan: Locked to specific instance family in a region

---

### Question 5 — Dedicated Hosts vs Dedicated Instances
**Scenario**: A company needs to run Oracle Database on EC2 and their Oracle license is based on per-physical-core licensing. Which option meets the licensing requirement?

**Answer**: **EC2 Dedicated Host**

**Why correct**: Dedicated Hosts give you visibility into the physical server (socket count, core count), which is required for per-core/per-socket licensing. Dedicated Instances don't provide this visibility.

---

### Question 6 — Instance Store vs EBS
**Scenario**: An application needs the highest possible IOPS for a temporary cache that processes incoming data streams. Data loss is acceptable since data is replicated elsewhere. What storage type should be used?

**Answer**: **Instance Store (NVMe-based ephemeral storage)**

**Why correct**: Instance Store provides millions of IOPS with the lowest latency since it's physically attached to the host. Data loss is acceptable per the requirements.

**Why EBS is wrong**: Even io2 Block Express maxes at 256,000 IOPS. Instance Store can exceed 3 million IOPS.

---

### Question 7 — IMDSv2 Security
**Scenario**: A security audit reveals that EC2 instances are vulnerable to SSRF attacks that could expose IAM role credentials from the instance metadata service. What should be done?

**Answer**: **Require IMDSv2 (disable IMDSv1) on all instances**

**Why correct**: IMDSv2 requires a session token obtained via a PUT request, which prevents SSRF exploits that can only send GET requests. IMDSv1 allows simple GET requests that SSRF can exploit.

---

### Question 8 — Cross-Region AMI
**Scenario**: A company has a custom AMI in us-east-1 and needs to launch the same application in eu-west-1 for DR. What steps are required?

**Answer**: **Copy the AMI from us-east-1 to eu-west-1, then launch instances from the copied AMI**

**Why correct**: AMIs are regional. You MUST copy them to use in another region. The copy includes the EBS snapshots.

---

### Question 9 — Auto Scaling with Mixed Instances
**Scenario**: A web application needs to handle variable traffic while minimizing costs. The application is stateless and runs on Linux. How should this be architected?

**Answer**: **Auto Scaling Group with mixed instance types using On-Demand for baseline and Spot for scaling, behind an ALB**

**Why correct**: On-Demand provides reliable baseline capacity. Spot fills variable demand at up to 90% off. Mixed instances across instance types reduce Spot interruption risk. ALB distributes traffic across all healthy instances.

---

### Question 10 — EBS Multi-Attach
**Scenario**: A clustered application requires that multiple EC2 instances access the same block storage volume simultaneously. What should be used?

**Answer**: **io1 or io2 EBS volume with Multi-Attach enabled (instances must be in the same AZ)**

**Why correct**: Multi-Attach allows a single io1/io2 volume to be attached to up to 16 Nitro-based instances in the same AZ. The application must manage concurrent writes.

**Why EFS is wrong**: The question specifies "block storage" — EFS is file storage.

---

### Question 11 — Hibernate
**Scenario**: A company has instances that take 10 minutes to boot due to large in-memory caches. They want to stop instances overnight to save costs but start quickly in the morning. What feature should they use?

**Answer**: **EC2 Hibernate**

**Why correct**: Hibernate saves the RAM contents to the EBS root volume. When started, RAM is reloaded and the instance resumes in seconds with its in-memory cache intact.

**Requirements**: EBS root volume must be encrypted, instance must have been launched with hibernate option enabled, RAM must be < 150 GB.

### Question 12 — Capacity Reservations
**Scenario**: A company needs to guarantee that they can launch 50 m5.xlarge instances in us-east-1a during a critical event next month. How can they ensure capacity?

**Answer**: **Create an On-Demand Capacity Reservation for 50 m5.xlarge in us-east-1a**

**Why correct**: Capacity Reservations guarantee that instance capacity is available when you need it, even during AWS capacity shortages. You can combine with Savings Plans for discounts.

### Question 13 — Elastic IP
**Scenario**: An application uses a third-party API that requires whitelisting a static IP address. The EC2 instance may be stopped and started for maintenance. What ensures the IP doesn't change?

**Answer**: **Associate an Elastic IP address with the instance**

**Why correct**: Elastic IPs are static public IPv4 addresses that persist even when an instance is stopped/started. Regular public IPs change on stop/start.

**Exam Note**: You're charged for Elastic IPs that are NOT associated with a running instance ($0.005/hour). This is to encourage releasing unused IPs.

### Question 14 — Nitro Enclaves
**Scenario**: A healthcare company needs to process sensitive patient data on EC2 but requires that even AWS administrators cannot access the data during processing. What should they use?

**Answer**: **EC2 Nitro Enclaves**

**Why correct**: Nitro Enclaves create isolated compute environments that nobody — not even root users on the instance, or AWS support — can SSH into or access. Data is processed in a cryptographically isolated enclave.

### Question 15 — Migration Strategy
**Scenario**: A company wants to migrate 500 on-premises VMs to AWS as quickly as possible with minimal changes. Which approach should they use?

**Answer**: **AWS Application Migration Service (MGN) for lift-and-shift to EC2**

**Why correct**: MGN (formerly CloudEndure) provides automated rehost (lift-and-shift) migration. It continuously replicates VMs to AWS, then you perform a cutover. Minimal changes needed.

## 10. Configuration Details

### Launching an EC2 Instance — Step by Step (Console)

1. **Choose an AMI**
   - Amazon Linux 2023 (free tier eligible, AWS-optimized)
   - Ubuntu Server 22.04 LTS
   - Windows Server 2022

2. **Choose an Instance Type**
   - t3.micro (1 vCPU, 1 GB RAM) — Free tier eligible
   - m5.large (2 vCPU, 8 GB RAM) — Good for small production workloads

3. **Configure Instance Details**
   - Number of instances
   - VPC and Subnet
   - Auto-assign Public IP (enable for public-facing instances)
   - IAM Role (CRITICAL: use roles, NEVER embed access keys)
   - Shutdown Behavior: Stop (default) or Terminate
   - Enable Termination Protection (prevents accidental deletion)
   - Monitoring: Enable detailed monitoring (1-minute intervals vs default 5-minute)
   - Tenancy: Shared (default), Dedicated Instance, or Dedicated Host
   - User Data: Bootstrap script

4. **Add Storage**
   - Root volume: gp3, 8 GB minimum (Linux), 30 GB (Windows)
   - Additional volumes as needed
   - Encryption: Enable (uses KMS)
   - Delete on Termination: Yes (default for root) or No

5. **Add Tags**
   - Name: MyWebServer
   - Environment: Production
   - Owner: team-name

6. **Configure Security Group**
   - SSH (port 22) from your IP only (NOT 0.0.0.0/0!)
   - HTTP (port 80) from 0.0.0.0/0 (if web server)
   - HTTPS (port 443) from 0.0.0.0/0 (if web server)

7. **Key Pair**
   - Create or select existing key pair (for SSH access)
   - Download .pem file (KEEP SAFE — you can't download it again)

## 13. Additional Critical Information

### Best Practices Checklist (20+)

1. ✅ Use IAM Roles — NEVER embed access keys in instances
2. ✅ Use IMDSv2 — Disable v1 to prevent SSRF attacks
3. ✅ Enable termination protection for production instances
4. ✅ Use multiple Availability Zones for high availability
5. ✅ Tag EVERY resource (Name, Environment, Owner, CostCenter)
6. ✅ Encrypt all EBS volumes using KMS
7. ✅ Restrict Security Group ingress to specific IPs (never 0.0.0.0/0 for SSH)
8. ✅ Use Systems Manager Session Manager instead of SSH (no need for key pairs or port 22)
9. ✅ Right-size instances using CloudWatch metrics and Compute Optimizer
10. ✅ Use Graviton instances for 40% better price-performance (if application supports Arm)
11. ✅ Implement Auto Scaling for variable workloads
12. ✅ Use Savings Plans or RIs for steady-state workloads
13. ✅ Use Spot for fault-tolerant batch workloads
14. ✅ Create custom AMIs for consistent deployments (Golden AMI pattern)
15. ✅ Enable detailed monitoring (1-minute intervals) for production
16. ✅ Use VPC endpoints to access AWS services without internet
17. ✅ Implement backup strategy (EBS snapshots, AMIs)
18. ✅ Use placement groups for HPC/low-latency needs
19. ✅ Monitor and clean up unused EBS volumes, snapshots, and Elastic IPs
20. ✅ Use EC2 Instance Connect Endpoint for secure SSH without bastion hosts

### Common Mistakes (15+)

1. ❌ Leaving SSH (port 22) open to 0.0.0.0/0
2. ❌ Using access keys instead of IAM roles
3. ❌ Forgetting to encrypt EBS volumes
4. ❌ Not using Multi-AZ deployments for critical workloads
5. ❌ Over-provisioning instances (paying for unused CPU/memory)
6. ❌ Under-provisioning T-series instances (running out of CPU credits)
7. ❌ Forgetting to release Elastic IPs after terminating instances (you get charged)
8. ❌ Not setting up CloudWatch alarms for CPU, disk, status checks
9. ❌ Using IMDSv1 (vulnerable to SSRF)
10. ❌ Not tagging resources (impossible to track costs)
11. ❌ Running databases on EC2 when RDS/Aurora would be better
12. ❌ Not testing instance recovery (what happens if an instance dies?)
13. ❌ Storing application state on the instance (instances can be terminated)
14. ❌ Not using launch templates (using launch configurations which are legacy)
15. ❌ Forgetting that stopping an instance changes its public IP (use Elastic IP if static IP needed)

### Exam Tips and Traps

1. **"Minimum cost" + "fault tolerant"** = Spot Instances
2. **"Steady workload" + "cost optimization"** = Reserved Instances or Savings Plans
3. **"Per-core licensing"** = Dedicated Host (NOT Dedicated Instance)
4. **"Lowest latency between instances"** = Cluster Placement Group
5. **"Instance fails, must survive"** = Spread Placement Group
6. **"Big data, Hadoop, Cassandra"** = Partition Placement Group
7. **"Can't connect to instance"** = Check Security Group, Route Table, NACL, Internet Gateway
8. **"Need to encrypt existing unencrypted EBS"** = Snapshot → Copy with encryption → Create new volume
9. **"Application slow on T-series"** = CPU credit exhaustion
10. **"Need static IP that survives stop/start"** = Elastic IP
11. **Always choose GRAVITON** if the question mentions cost optimization and the app supports Arm/Linux
12. **Auto Scaling** almost always appears with EC2 — if the question involves variable load, the answer likely includes ASG
