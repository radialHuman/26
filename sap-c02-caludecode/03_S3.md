# 03 — Amazon S3 (Simple Storage Service) — Exhaustive Deep-Dive

---

## 1. What Problem S3 Solves

### The World Before S3

Before cloud storage, storing files meant:

1. **Buy storage hardware** — SAN (Storage Area Network) devices cost $50,000–$500,000. Hard drives fail. You need RAID, redundancy, backups.
2. **Capacity planning nightmares** — Running out of storage meant emergency hardware purchases. Over-buying meant wasted money.
3. **Backup complexity** — You had to manage tape backups, offsite copies, rotation schedules. Restoring from tape could take days.
4. **Scaling was painful** — When you hit storage limits, you couldn't just add more. You had to migrate to bigger systems.
5. **No durability guarantees** — A fire, flood, or catastrophic hardware failure could destroy all your data.

### What S3 Changed

S3 was AWS's **very first service** (launched March 14, 2006). It provides virtually unlimited object storage with 99.999999999% (11 nines) durability.

| Before S3 | After S3 |
|---|---|
| Buy storage hardware ($50K+) | Pay per GB ($0.023/GB/month for Standard) |
| Limited capacity | Virtually unlimited (no capacity planning) |
| You manage redundancy | AWS replicates across 3+ AZs automatically |
| 99.99% durability (enterprise SAN) | 99.999999999% durability (11 nines) |
| Backup is your problem | Built-in versioning, replication, lifecycle |
| Fixed capacity | Scales from 0 to exabytes automatically |

### What Does "11 Nines Durability" Mean?

If you store **10,000,000 (10 million) objects** in S3, you can expect to lose **1 object every 10,000 years**. That's durability.

This is achieved by automatically storing your data across **a minimum of 3 Availability Zones** (physically separate data centers), with multiple copies in each.

### Real-World Examples

- **Netflix** stores all of its movie and TV show master files, encoding pipeline outputs, and logs in S3
- **Airbnb** stores millions of property photos in S3
- **NASA** stores satellite imagery and scientific data
- **Dropbox** was originally built entirely on top of S3

### Object Storage vs Block Storage vs File Storage

Understanding this distinction is fundamental:

| Feature | Object Storage (S3) | Block Storage (EBS) | File Storage (EFS) |
|---|---|---|---|
| Data unit | Objects (files + metadata) | Fixed-size blocks | Files in directories |
| Access method | HTTP API (GET/PUT) | Mounted as disk drive | NFS/SMB mount |
| Hierarchy | Flat namespace (bucket + key) | None (raw blocks) | Directory tree |
| Modify part of file? | No — replace entire object | Yes — change specific blocks | Yes — edit in place |
| Max size | 5 TB per object | 64 TB per volume | Unlimited |
| Performance | High throughput | Low latency, high IOPS | Moderate |
| Use case | Backups, media, data lakes | OS boot drives, databases | Shared file systems |
| Mounted to OS? | No (accessed via API/SDK) | Yes (appears as /dev/xvdf) | Yes (appears as /mnt/efs) |

**Exam Key**: S3 is NOT a filesystem. You can't mount it as a drive (use EFS for that). You can't edit part of a file (you must re-upload the entire object).

## 3. When to Use S3

### 10+ Use Cases

1. **Static website hosting** — Serve HTML, CSS, JS, images directly from S3 + CloudFront
2. **Data lake foundation** — Store raw data (structured, semi-structured, unstructured) for analytics
3. **Backup and archival** — Automated backups from servers, databases, applications
4. **Media storage** — Photos, videos, audio files for web/mobile apps
5. **Big data analytics input** — Source data for Athena, Redshift Spectrum, EMR, Glue
6. **Log storage** — CloudTrail logs, VPC Flow Logs, ELB access logs, application logs
7. **Software distribution** — Distribute software packages, updates, patches
8. **Disaster recovery** — Cross-region replication for DR, database backups
9. **Machine learning training data** — Store and version training datasets for SageMaker
10. **Data transfer staging** — Intermediate storage for ETL pipelines, data migrations
11. **Compliance/legal hold** — S3 Object Lock for WORM (Write Once Read Many) compliance
12. **Content delivery origin** — Origin for CloudFront CDN distribution

### 5+ Anti-Patterns (When NOT to Use S3)

1. **Don't use as a filesystem** — S3 is NOT a filesystem. No directory locking, no POSIX compliance. Use EFS or FSx for shared file systems.
2. **Don't use for frequently changing data** — Every change requires re-uploading the entire object. Use EBS or a database.
3. **Don't use for ultra-low-latency access** — S3 has ~100-200ms latency. For sub-millisecond, use ElastiCache or DynamoDB DAX.
4. **Don't use for structured query access** — If you need SQL queries on live data, use RDS. (S3 + Athena works for analytics but not transactional workloads.)
5. **Don't use for OS boot volumes** — Use EBS. S3 can't be mounted as a block device.
6. **Don't use for databases** — While you can store database backups in S3, don't run a database on S3 storage.

### Glacier Retrieval Speeds

| Retrieval Tier | Glacier Flexible | Glacier Deep Archive |
|---|---|---|
| Expedited | 1-5 minutes | N/A |
| Standard | 3-5 hours | 12 hours |
| Bulk | 5-12 hours | 48 hours |

### S3 Intelligent-Tiering (Exam Favorite!)

Automatically moves objects between tiers based on access patterns. No retrieval fees.

Tiers:
- **Frequent Access** (objects accessed within 30 days) → Standard pricing
- **Infrequent Access** (not accessed for 30 days) → 40% savings
- **Archive Instant Access** (not accessed for 90 days) → 68% savings
- **Archive Access** (optional, not accessed for 90+ days) → Glacier pricing
- **Deep Archive Access** (optional, not accessed for 180+ days) → Deep Archive pricing

Monitoring fee: $0.0025 per 1,000 objects/month

**When to use**: When you don't know (or can't predict) how often data will be accessed.

## 5. How S3 Works Under the Hood

### Architecture

S3 is a **distributed system** across multiple data centers:

1. When you upload an object, S3 stores it across **at least 3 Availability Zones** (for Standard class)
2. Each AZ stores multiple copies on different physical devices
3. Before S3 returns a success response, it confirms the data is durably stored in multiple AZs
4. If any copy fails, S3 automatically repairs it from other copies (self-healing)

### Consistency Model (Changed in December 2020!)

**Before December 2020** (old behavior — still referenced in some study materials):
- PUTs of NEW objects: Read-after-write consistency
- PUTs (overwrite) and DELETEs: Eventual consistency (you might read stale data briefly)

**After December 2020 (CURRENT — what the exam tests)**:
- **Strong read-after-write consistency** for ALL operations
- After a successful PUT, any subsequent GET will return the latest version
- After a DELETE, any subsequent GET will return "object not found"
- This applies to S3 LIST operations too
- **No additional cost, no performance impact**

### Multipart Upload

For files over 100 MB (required for files over 5 GB):
1. Initiate multipart upload (S3 assigns an upload ID)
2. Upload file in parts (each 5 MB–5 GB, up to 10,000 parts)
3. Parts can upload in parallel (faster!)
4. If a part fails, just retry that part (not the whole file)
5. Complete multipart upload (S3 assembles all parts)

**Exam Tip**: S3 Transfer Acceleration uses AWS edge locations to accelerate uploads — particularly useful for users far from the S3 bucket's region.

### Request Performance

S3 scales to handle massive request rates:
- **3,500 PUT/COPY/POST/DELETE requests per second per prefix**
- **5,500 GET/HEAD requests per second per prefix**

A "prefix" is the path before the object name: `bucket/folder1/subfolder1/file.txt` → prefix is `folder1/subfolder1/`

**To maximize performance**: Spread objects across multiple prefixes. Example: Instead of putting all objects under `/data/`, use `/data/2024/01/`, `/data/2024/02/`, etc.

## 6. Basic Components and Working

### Buckets

- A container for objects (like a top-level folder)
- Bucket names are **globally unique** across ALL AWS accounts
- Bucket names must be 3–63 characters, lowercase, numbers, hyphens (no underscores!)
- You choose the region for a bucket — objects stay in that region unless you replicate them
- No limit on number of objects in a bucket
- Flat structure (no real folders — S3 simulates folders using key prefixes with `/`)

### Objects

- A file + metadata, stored with a unique key
- **Key**: The full path/name (e.g., `photos/2024/vacation/beach.jpg`)
- **Value**: The file content (0 bytes to 5 TB max)
- **Metadata**: System metadata (Content-Type, Last-Modified) + user-defined metadata
- **Version ID**: If versioning is enabled
- **Tags**: Key-value pairs for management and cost allocation

### Versioning

When enabled:
- Every object upload creates a new version (keeps ALL previous versions)
- Deleting an object adds a **delete marker** (previous versions still exist)
- To truly delete: delete the specific version
- **Cannot be disabled once enabled** — only suspended
- **Required for Cross-Region Replication**

**Exam Critical**: Versioning protects against accidental deletion. With MFA Delete, you need MFA to permanently delete versions.

### Lifecycle Policies

Automate transitioning objects between storage classes or deleting them:

```
Example Lifecycle Rule:
Day 0:    Object uploaded → S3 Standard
Day 30:   Transition to → Standard-IA (cheaper, still fast)
Day 90:   Transition to → Glacier Instant Retrieval (much cheaper)
Day 365:  Transition to → Glacier Deep Archive (cheapest)
Day 730:  Delete permanently
```

Can apply to:
- Current versions
- Previous versions (if versioning is enabled)
- Incomplete multipart uploads (clean up failed uploads)

### Replication (EXAM CRITICAL!)

| Feature | CRR (Cross-Region Replication) | SRR (Same-Region Replication) |
|---|---|---|
| Source and destination | Different AWS regions | Same AWS region |
| Use case | DR, compliance, latency reduction | Log aggregation, live replication between accounts |
| Requirement | Versioning enabled on BOTH buckets | Versioning enabled on BOTH buckets |
| Scope | Entire bucket or by prefix/tag | Entire bucket or by prefix/tag |
| Existing objects? | NOT replicated automatically (use S3 Batch Replication) | NOT replicated automatically |
| Delete markers? | Optional (can choose to replicate or not) | Optional |
| Chaining? | NO — A→B, B→C does NOT mean A→C automatically | NO |

### Bucket Policies (IAM for S3)

JSON-based policies attached directly to buckets. Used for:
- Cross-account access (the most common use case on the exam)
- Public access
- Enforce encryption
- Restrict by IP address or VPC

**Example: Cross-Account Access**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCrossAccountAccess",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:root"
      },
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}
```

**Example: Force HTTPS Only**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ForceHTTPS",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
```

### S3 Access Control — The Three Mechanisms

1. **IAM Policies** — Attached to IAM users/roles/groups. Controls what AWS principals can do.
2. **Bucket Policies** — Attached to buckets. Controls who can access the bucket. Best for cross-account access.
3. **ACLs (Access Control Lists)** — Legacy. AWS recommends disabling ACLs. Bucket Ownership controls (BucketOwnerEnforced) disable ACLs.

**Priority**: If ANY policy grants access AND no explicit DENY exists, access is allowed. An explicit DENY always wins.

### S3 Event Notifications

S3 can trigger events when objects are created, deleted, or modified:

Destinations:
- **Lambda** — Run code in response to S3 events
- **SQS** — Queue messages for processing
- **SNS** — Fan out notifications
- **EventBridge** — Route to 18+ targets, filter, transform

**Example**: Photo uploaded to S3 → triggers Lambda → creates thumbnail → stores in S3

### S3 Select and Glacier Select

Query inside objects using SQL without downloading the entire object:
- Filter rows and columns from CSV/JSON/Parquet files
- Transfer only the data you need (reduces data transfer costs and time)

### S3 Transfer Acceleration

Uses CloudFront edge locations to speed up uploads:
- Client uploads to the nearest edge location
- AWS uses its internal backbone network to transfer to S3 (faster than public internet)
- Useful for global users uploading to a single region

### Presigned URLs

Temporary URLs that grant time-limited access to private S3 objects:
- Generated by an authorized user/role
- Anyone with the URL can access the object for the specified duration
- Use case: Allow a customer to download a private file without making it public

```bash
aws s3 presign s3://my-bucket/my-file.pdf --expires-in 3600
```

### S3 Object Lock

WORM (Write Once Read Many) protection:
- **Governance Mode**: Users with special permission CAN delete/overwrite
- **Compliance Mode**: NO ONE can delete/overwrite (not even root account) until the retention period expires
- **Legal Hold**: Prevents deletion indefinitely until explicitly removed (independent of retention period)

**Exam Use Case**: Financial records that must be retained for 7 years → Compliance Mode with 7-year retention.

### S3 Access Points

Simplify managing access to shared datasets:
- Each access point has its own DNS name
- Each can have its own permissions policy
- Can restrict to specific VPC (VPC-only access points)

Example: A data lake bucket with an access point for the analytics team (read-only) and another for the data engineering team (read-write).

## 7. Encryption — Deep-Dive (EXAM CRITICAL!)

### Server-Side Encryption (SSE) — Data encrypted at rest by S3

| Type | Who Manages Key? | Key Storage | When to Use | Exam Note |
|---|---|---|---|---|
| **SSE-S3** | AWS manages everything | S3 internal | Default, simplest option | Default since Jan 2023 |
| **SSE-KMS** | You manage via KMS | AWS KMS | Compliance requiring key control, audit trail | CloudTrail logs every key use. Watch for KMS throttling! |
| **SSE-C** | YOU provide the key with every request | You store it yourself | Full customer key control | S3 does NOT store your key. HTTPS required. |

### Client-Side Encryption

- YOU encrypt data BEFORE uploading to S3
- S3 sees only encrypted blobs
- YOU manage keys entirely
- Use case: Maximum security, S3 never sees plaintext

### Exam Critical Encryption Scenarios

1. **"Need audit trail of when encryption keys were used"** → SSE-KMS (CloudTrail logs KMS API calls)
2. **"Default encryption for all objects"** → SSE-S3 (or SSE-KMS as bucket default)
3. **"Customer must control their own encryption keys but doesn't want to manage KMS"** → SSE-C
4. **"S3 must never have access to unencrypted data"** → Client-Side Encryption
5. **"High-throughput uploads getting throttled"** → SSE-KMS has a quota (5,500–30,000 requests/second per region for GenerateDataKey). Switch to SSE-S3 or request KMS quota increase.

**Exam Trap**: SSE-KMS uses an envelope encryption approach. S3 calls KMS GenerateDataKey for each object → this can hit KMS request quotas for high-throughput workloads!

## 8. Pros and Cons

### Pros

1. **11 nines durability** — Virtually indestructible data storage
2. **Unlimited scale** — No capacity planning, no limits on total storage
3. **Multiple storage classes** — Optimize cost from hot to cold data
4. **Lifecycle automation** — Automatically transition data to cheaper tiers
5. **Versioning** — Built-in protection against accidental deletion
6. **Replication** — Cross-region and same-region for DR and compliance
7. **Event-driven** — Trigger Lambda, SQS, SNS, EventBridge on object events
8. **Encryption** — Multiple options (SSE-S3, SSE-KMS, SSE-C, client-side)
9. **Cost-effective** — Glacier Deep Archive at $0.00099/GB/month for archival
10. **Global accessibility** — Accessible from anywhere via HTTPS
11. **Intelligent-Tiering** — Zero-effort cost optimization
12. **Strong consistency** — No more eventual consistency issues

### Cons

1. **Not a filesystem** — Can't mount, can't edit in place, no file locking
2. **5 TB per object limit** — Single objects can't exceed 5 TB
3. **Retrieval costs** — IA/Glacier classes charge per-GB retrieval fees
4. **Minimum storage duration charges** — IA: 30 days, Glacier: 90 days, Deep Archive: 180 days
5. **Bucket name globally unique** — Good names are taken, and you can't rename a bucket
6. **100-200ms latency** — Not suitable for real-time, sub-millisecond workloads
7. **Eventual consistency for bucket operations** — Creating/deleting buckets may have brief propagation delay
8. **Costs can surprise** — Data transfer out, request costs, and retrieval fees add up
9. **No append operation** — Can't add data to an existing object; must re-upload entire object
10. **Public access risks** — Misconfigured bucket policies can expose data (AWS now blocks public access by default)

## 9. SAP-C02 Exam Questions (15+ Scenarios)

### Question 1 — Storage Class Selection
**Scenario**: A company stores application log files in S3. Logs are analyzed daily for the first week, then accessed about once per quarter for compliance audits. Logs must be retained for 7 years. How should they design the storage?

**Answer**: Use a Lifecycle Policy:
- Days 0-30: S3 Standard
- Days 30-90: S3 Standard-IA
- Days 90-365: S3 Glacier Instant Retrieval (for quarterly access with millisecond retrieval)
- Day 365+: S3 Glacier Deep Archive (cheapest, accessed only if needed)
- Day 2,555 (7 years): Delete

---

### Question 2 — Cross-Account Access
**Scenario**: Account A needs to read objects from a bucket in Account B. What is the simplest approach?

**Answer**: **Bucket policy on Account B's bucket granting access to Account A's IAM role**

```json
{
  "Effect": "Allow",
  "Principal": {"AWS": "arn:aws:iam::ACCOUNT_A_ID:role/ReadRole"},
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::account-b-bucket/*"
}
```

**Why not ACLs**: AWS recommends against ACLs. Bucket policies are the standard approach.

---

### Question 3 — Encryption Compliance
**Scenario**: A healthcare company must encrypt all S3 data at rest, log every key access for auditing, and rotate keys annually. What should they use?

**Answer**: **SSE-KMS with a customer-managed CMK (Customer Master Key)**

**Why**: KMS provides automatic key rotation (annual), CloudTrail logs every Encrypt/Decrypt/GenerateDataKey call, and the customer controls the key policy.

---

### Question 4 — Replication Requirements
**Scenario**: A company needs disaster recovery for S3 data. Their primary bucket is in us-east-1 and they need a copy in eu-west-1. What must they configure?

**Answer**: **S3 Cross-Region Replication (CRR)**

**Requirements**:
1. Enable versioning on BOTH source and destination buckets
2. Create CRR rule on source bucket
3. IAM role that S3 assumes to replicate objects

**Important**: Existing objects are NOT replicated automatically — use S3 Batch Replication for existing objects.

---

### Question 5 — KMS Throttling
**Scenario**: An application uploads 10,000 files per second to S3 with SSE-KMS encryption. Upload failures are occurring with "ThrottlingException". What should be done?

**Answer**: Options (pick best for scenario):
1. **Request a KMS quota increase** (GenerateDataKey quota)
2. **Switch to SSE-S3** (if KMS audit trail is not required)
3. **Use S3 Bucket Key** — Reduces KMS API calls by up to 99% by using a bucket-level key that S3 caches

**Exam Tip**: S3 Bucket Key is the modern answer to KMS throttling. It generates a short-lived bucket-level key from KMS, then uses it locally for encrypting multiple objects.

---

### Question 6 — S3 + CloudFront
**Scenario**: A company serves a static website from S3. They want to ensure users can ONLY access the content through CloudFront, not directly from the S3 URL. How?

**Answer**: **Use an Origin Access Control (OAC)** policy that grants CloudFront access to the S3 bucket, and remove all public access from the bucket.

**Note**: Origin Access Identity (OAI) is the older method — OAC is the current recommendation. Exam may reference either.

---

### Question 7 — Compliance with Object Lock
**Scenario**: A financial institution must store trade records for 7 years. Records must be immutable — no one (not even the root account) should be able to delete them during the retention period. What should they use?

**Answer**: **S3 Object Lock in Compliance Mode with 7-year retention period**

**Why not Governance Mode**: Governance allows users with special permissions (s3:BypassGovernanceRetention) to delete objects. Compliance mode prevents ALL deletions.

---

### Question 8 — Event-Driven Architecture
**Scenario**: When a user uploads a video to S3, the system should: (1) create a thumbnail, (2) update a database record, and (3) send a notification email. How should this be architected?

**Answer**: S3 Event Notification → **Amazon EventBridge** → Three rules:
1. Rule 1 → Lambda (create thumbnail)
2. Rule 2 → Lambda (update database)
3. Rule 3 → SNS (send email)

**Why EventBridge over S3 Event Notifications to SNS**: EventBridge supports filtering, transformation, multiple targets, archive/replay, and is the recommended approach for new architectures.

---

### Question 9 — Cost Optimization
**Scenario**: A data lake has 500 TB of data. Analysis shows: 50 TB accessed frequently, 200 TB accessed monthly, 250 TB accessed rarely. The team doesn't want to manually manage storage classes. What should they use?

**Answer**: **S3 Intelligent-Tiering**

**Why**: Automatically moves objects based on access patterns. No retrieval fees. Monitoring cost ($0.0025/1000 objects) is negligible compared to storage savings.

---

### Question 10 — Presigned URLs
**Scenario**: An application needs to allow anonymous users to download a specific file from a private S3 bucket for 1 hour after purchase. How?

**Answer**: **Generate a presigned URL with 1-hour expiration** when the user completes purchase. The URL grants temporary GET access to the specific object.

---

### Question 11 — Versioning + MFA Delete
**Scenario**: A company had an incident where an employee accidentally deleted critical S3 data. How to prevent this in the future?

**Answer**:
1. **Enable Versioning** — Deletes add a delete marker but previous versions are preserved
2. **Enable MFA Delete** — Requires MFA to permanently delete versions or suspend versioning
3. **Add a Lifecycle rule to retain versions** for a period before permanent deletion

---

### Question 12 — S3 Access Points
**Scenario**: A data lake in a single S3 bucket is shared by 5 teams, each needing different access permissions. Maintaining a single bucket policy has become unmanageable. What should they do?

**Answer**: **Create S3 Access Points** — one per team, each with its own access policy. This simplifies policy management.

---

### Question 13 — S3 Transfer Acceleration
**Scenario**: Users in Asia and Europe upload large files (1-10 GB) to an S3 bucket in us-east-1. Upload speeds are slow. How to improve?

**Answer**: **Enable S3 Transfer Acceleration** on the bucket. Users upload to the nearest AWS edge location, and AWS transfers over its private backbone to the S3 bucket.

Can combine with multipart upload for maximum speed.

---

### Question 14 — Cross-Region Replication + Encryption
**Scenario**: A company replicates S3 data from us-east-1 to eu-west-1 using CRR. Objects in the source are encrypted with SSE-KMS using a CMK in us-east-1. What's required for replication?

**Answer**: 
1. The replication rule must specify the destination KMS key (a CMK in eu-west-1)
2. The IAM replication role needs kms:Decrypt permission for the source key and kms:Encrypt for the destination key
3. KMS keys are regional — you CANNOT use the same KMS key in both regions

---

### Question 15 — S3 Batch Operations
**Scenario**: A company has 10 billion existing objects that need to be: (a) copied to a different storage class, or (b) encrypted with a different KMS key, or (c) replicated to another bucket. How?

**Answer**: **S3 Batch Operations** — Can perform operations on billions of objects at scale. Works with S3 Inventory (to get the list of objects) or a CSV manifest.

## 10. Configuration Details

### Creating a Bucket with Proper Settings

```bash
# Create bucket
aws s3api create-bucket --bucket my-bucket-unique-name --region us-east-1

# Enable versioning
aws s3api put-bucket-versioning --bucket my-bucket-unique-name \
  --versioning-configuration Status=Enabled

# Enable default encryption (SSE-S3)
aws s3api put-bucket-encryption --bucket my-bucket-unique-name \
  --server-side-encryption-configuration '{
    "Rules": [{"ApplyServerSideEncryptionByDefault": {"SSEAlgorithm": "AES256"}}]
  }'

# Block all public access
aws s3api put-public-access-block --bucket my-bucket-unique-name \
  --public-access-block-configuration '{
    "BlockPublicAcls": true,
    "IgnorePublicAcls": true,
    "BlockPublicPolicy": true,
    "RestrictPublicBuckets": true
  }'

# Enable S3 Bucket Key (reduces KMS costs if using SSE-KMS)
aws s3api put-bucket-encryption --bucket my-bucket-unique-name \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "arn:aws:kms:us-east-1:123456789012:key/xxx"
      },
      "BucketKeyEnabled": true
    }]
  }'

# Create lifecycle rule
aws s3api put-bucket-lifecycle-configuration --bucket my-bucket-unique-name \
  --lifecycle-configuration '{
    "Rules": [{
      "ID": "ArchiveOldData",
      "Status": "Enabled",
      "Filter": {"Prefix": "logs/"},
      "Transitions": [
        {"Days": 30, "StorageClass": "STANDARD_IA"},
        {"Days": 90, "StorageClass": "GLACIER"},
        {"Days": 365, "StorageClass": "DEEP_ARCHIVE"}
      ],
      "Expiration": {"Days": 2555}
    }]
  }'
```

## 12. Additional Critical Information

### Best Practices (20+)

1. ✅ Enable versioning on all important buckets
2. ✅ Enable default encryption (SSE-S3 minimum, SSE-KMS for compliance)
3. ✅ Block all public access unless specifically needed
4. ✅ Use S3 Bucket Keys with SSE-KMS to reduce KMS costs and throttling
5. ✅ Use lifecycle policies to transition to cheaper storage classes
6. ✅ Enable S3 Intelligent-Tiering for unpredictable access patterns
7. ✅ Use CRR for disaster recovery
8. ✅ Use VPC Gateway Endpoint for private, free S3 access
9. ✅ Enable CloudTrail data events for S3 access logging
10. ✅ Enable S3 Server Access Logging for detailed request logs
11. ✅ Use presigned URLs (not public buckets) for temporary access
12. ✅ Use multipart upload for files over 100 MB
13. ✅ Use Transfer Acceleration for global uploads
14. ✅ Use S3 Access Points for multi-team data lakes
15. ✅ Distribute objects across prefixes for high request rates
16. ✅ Use S3 Object Lock for compliance/regulatory requirements
17. ✅ Clean up incomplete multipart uploads with lifecycle rules
18. ✅ Monitor with S3 Storage Lens for organization-wide visibility
19. ✅ Use S3 Inventory for large-scale object auditing
20. ✅ Use S3 Batch Operations for bulk operations

### Common Mistakes (15+)

1. ❌ Making buckets public (data breach risk — this is how most S3 breaches happen)
2. ❌ Not enabling versioning (one accidental delete = data gone forever)
3. ❌ Not setting lifecycle policies (paying Standard price for data never accessed)
4. ❌ Using NAT Gateway to access S3 instead of free Gateway Endpoint
5. ❌ Not understanding minimum storage duration charges (deleting Glacier data early = charged for 90 days anyway)
6. ❌ Using SSE-KMS without considering throttling for high-throughput workloads
7. ❌ Not enabling MFA Delete for critical buckets
8. ❌ Forgetting that CRR requires versioning on BOTH buckets
9. ❌ Assuming existing objects are replicated when enabling CRR (they're not — use Batch Replication)
10. ❌ Not monitoring costs (data transfer out and request costs add up)
11. ❌ Putting all objects under one prefix (throttling at 3,500 PUT/5,500 GET per prefix)
12. ❌ Ignoring S3 Block Public Access settings
13. ❌ Using ACLs instead of bucket policies
14. ❌ Not encrypting data at rest
15. ❌ Forgetting that S3 bucket names are globally unique (and can't be renamed)

### Key Limits

| Resource | Limit |
|---|---|
| Object size | 5 TB max (5 GB max per single PUT; use multipart for larger) |
| Buckets per account | 100 (can increase to 1,000) |
| Object key name | 1,024 bytes max |
| PUT/COPY/POST/DELETE | 3,500 requests/second per prefix |
| GET/HEAD | 5,500 requests/second per prefix |
| Multipart upload parts | 10,000 max |
| Lifecycle rules per bucket | 1,000 |
| Tags per object | 10 |
| Metadata per object | 2 KB for user-defined metadata |

### Exam Tips

1. **"Cheapest archival storage"** → S3 Glacier Deep Archive
2. **"Unknown access patterns"** → S3 Intelligent-Tiering
3. **"Millisecond retrieval from archive"** → S3 Glacier Instant Retrieval
4. **"Cross-region DR for S3"** → Cross-Region Replication (requires versioning)
5. **"Private S3 access from VPC"** → Gateway VPC Endpoint (free)
6. **"Audit encryption key usage"** → SSE-KMS + CloudTrail
7. **"Immutable records"** → S3 Object Lock (Compliance Mode)
8. **"Speed up global uploads"** → S3 Transfer Acceleration
9. **"S3 event triggers"** → Lambda, SQS, SNS, or EventBridge
10. **"KMS throttling on S3"** → Enable S3 Bucket Key
11. **"Query S3 data with SQL"** → Athena (serverless) or Redshift Spectrum
12. **"Static website"** → S3 + CloudFront with OAC
