# S3 (Simple Storage Service) - Complete Deep Dive

## 1. What Problem Did It Solve?

**Before S3 (2006):**
- Storage on physical disks/NAS/SAN ($1,000s-100,000s)
- Limited capacity (buy more hardware to expand)
- No redundancy without expensive RAID/replication
- Backups manual and error-prone
- No global distribution
- Scaling required hardware procurement

**Problem:** Storage is expensive, limited, difficult to scale, no built-in redundancy

**S3 Solution:**
- Unlimited storage (store petabytes)
- 11 9's durability (99.999999999%) - won't lose data
- Pay only for what you store ($0.023/GB/month)
- Automatic replication across facilities
- Global accessibility via HTTP
- Built-in versioning, lifecycle management

**Storage Evolution:**

**1990s: Network Attached Storage (NAS)**

## 3. When to Use It

### **Use S3 When:**

✅ **Static website hosting**
- HTML, CSS, JS files
- Images, videos
- No server needed

✅ **Data lake / long-term storage**
- Raw data dumps
- Log files
- Backups
- Archives

✅ **Application assets**
- User uploads (profile pictures, documents)
- Media files (videos, images)
- Software distribution (download apps)

✅ **Big data analytics**
- Store data for Athena queries
- EMR processing
- Redshift Spectrum

✅ **Disaster recovery**
- Backup databases
- Cross-region replication
- Immutable archives

✅ **CDN origin**
- CloudFront pulls from S3
- Distribute content globally

### **DON'T Use S3 When:**

❌ **Need file system** (mount as drive)
- Use EFS or FSx instead
- S3 is object storage (HTTP API), not file system

❌ **Frequent small updates** (modify parts of file)
- S3 = whole object upload/download
- Use database or EFS for frequently modified files

❌ **Low latency (<10ms) required**
- S3: 10-100ms latency
- Use ElastiCache or DynamoDB for sub-millisecond

❌ **Block storage for OS**
- Use EBS for EC2 boot volumes

❌ **Structured database queries**
- Use RDS, DynamoDB for transactional data

## 4. How Is It Different from Similar Services?

### **S3 vs EBS vs EFS**

| Feature | S3 | EBS | EFS |
|---------|----|----|-----|
| **Type** | Object storage | Block storage | File storage |
| **Access** | HTTP API | Attached to EC2 (like disk) | Mount as NFS |
| **Persistence** | Permanent | Survives stop (if configured) | Permanent |
| **Sharing** | Public/private URLs | One EC2 at a time | Multiple EC2 simultaneously |
| **Size** | Unlimited | 16 TB max per volume | Unlimited |
| **Cost** | $0.023/GB/month | $0.08/GB/month (gp3) | $0.30/GB/month |
| **Use case** | Static files, backups | OS disk, databases | Shared files |

---

### **S3 vs Glacier**

Glacier is S3 storage class (not separate service anymore):

| Class | Retrieval | Cost/GB/month | Use Case |
|-------|-----------|---------------|----------|
| **S3 Standard** | Instant | $0.023 | Active data |
| **S3 Glacier Instant** | Instant | $0.004 | Rare access, instant needed |
| **S3 Glacier Flexible** | 1min-12hr | $0.0036 | Archive, delay OK |
| **S3 Glacier Deep Archive** | 12-48hr | $0.00099 | Compliance, almost never accessed |

---

### **S3 vs Database (DynamoDB)**

| Feature | S3 | DynamoDB |
|---------|----| ---------|
| **Data type** | Any (files, objects) | Structured (JSON documents) |
| **Query** | List/get by key only | Query by attributes, indexes |
| **Latency** | 10-100ms | 1-10ms |
| **Cost** | Storage-based | Request-based or capacity-based |
| **Use case** | Files, unstructured data | Structured data, high throughput |

## 5. Underlying Mechanism and How It's Made

### **Technical Architecture:**

**How S3 Achieves 11 9's Durability:**

```
Upload object to S3:

1. Object arrives at S3 endpoint
2. S3 splits into chunks
3. Stores chunks across multiple:
   - Devices
   - Facilities (buildings)
   - Within same region

Replication:
- Minimum 3 copies (likely 6+ copies)
- Different physical locations
- Continuous integrity checking
- Auto-repair if corruption detected

Math:
- 11 9's = 99.999999999% durability
- If you store 10,000,000 objects
- Expect to lose 1 object every 10,000 years
```

---

### **Storage Organization:**

```
Bucket:
  └─ Objects (files)
      - Key (filename/path): photos/2026/image.jpg
      - Value (data): [binary data]
      - Metadata: Content-Type, custom headers
      - Version ID (if versioning enabled)
      
Flat structure (not real folders!):
  keys.txt
  photos/2026/01/img1.jpg
  photos/2026/01/img2.jpg
  
"Folders" are just key prefixes (UI illusion)
```

---

### **How Requests Work:**

```
PUT request (upload):
  1. Client → S3 API endpoint
  2. S3 authenticates (IAM/presigned URL)
  3. S3 writes to multiple devices
  4. Returns success only after durably stored
  5. Eventually consistent for overwrites (rare)

GET request (download):
  1. Client requests object
  2. S3 checks permissions
  3. Returns object from nearest/fastest copy
  4. Can use byte-range requests (partial download)
```

---

### **How Lifecycle Transitions Work:**

```
S3 Standard object stored

Lifecycle policy:
  - After 30 days → Move to Standard-IA
  - After 90 days → Move to Glacier Instant
  
AWS background process:
  - Daily scan of objects
  - Check age against policies
  - Transition storage class
  - Update metadata
  - Billing changes automatically

You don't see the movement (transparent)
```

## 6. Cost

### **Storage Costs (first 50 TB):**

```
S3 Standard: $0.023/GB/month
S3 Standard-IA: $0.0125/GB/month (45% cheaper)
S3 One Zone-IA: $0.01/GB/month (56% cheaper)
S3 Intelligent-Tiering: $0.023/GB + $0.0025 per 1,000 objects (monitoring fee)
S3 Glacier Instant: $0.004/GB/month (83% cheaper)
S3 Glacier Flexible: $0.0036/GB/month (84% cheaper)
S3 Glacier Deep Archive: $0.00099/GB/month (96% cheaper)
```

### **Request Costs:**

```
PUT/COPY/POST/LIST: $0.005 per 1,000 requests
GET/SELECT: $0.0004 per 1,000 requests

Retrieval costs (Glacier classes):
- Standard-IA: $0.01/GB retrieved
- Glacier Instant: $0.03/GB retrieved
- Glacier Flexible: $0.02-0.03/GB (depends on speed)
- Deep Archive: $0.02/GB
```

### **Data Transfer:**

```
Upload to S3: FREE
Download from S3 to internet: $0.09/GB (first 10 TB)
S3 to CloudFront: FREE
S3 to EC2 (same region): FREE
S3 Cross-Region Replication: $0.02/GB
```

### **Example Monthly Bill:**

```
100 TB stored:
- First 30 days in Standard: 100,000 GB × $0.023 = $2,300
- Transition to Glacier Flexible: 100,000 GB × $0.0036 = $360
- Savings: $1,940/month (84%)

With 1M GET requests: 1,000 × $0.0004 = $0.40
With 100K PUT requests: 100 × $0.005 = $0.50

Total in Glacier: $360.90/month
```

## 7. Pros and Cons

### **Pros ✅**

1. **Durability (11 9's)**
   - Virtually never lose data
   - Auto-replication
   - Auto-healing

2. **Unlimited storage**
   - No capacity planning
   - Store petabytes
   - Pay for what you use

3. **Cost-effective**
   - Cheapest storage option
   - Lifecycle policies auto-optimize costs
   - No provisioning costs

4. **Highly available**
   - 99.99% availability (Standard)
   - Multi-AZ replication
   - Global access

5. **Versioning**
   - Protect against accidental deletes
   - Track changes
   - Compliance

6. **Security**
   - Encryption (rest and transit)
   - Access control (IAM, bucket policies, ACLs)
   - MFA Delete
   - Object Lock

7. **Integration**
   - Works with all AWS services
   - Event notifications (Lambda triggers)
   - Analytics (Athena, Redshift Spectrum)

### **Cons ❌**

1. **Not a file system**
   - Can't mount as drive
   - No partial file updates
   - Whole object operations only

2. **Eventual consistency** (for overwrites/deletes)
   - Update object → Might see old version briefly
   - Rarely an issue but exists

3. **No locking**
   - Two writes to same key = last write wins
   - No database-style transactions

4. **Latency**
   - 10-100ms (vs microseconds for ElastiCache)
   - Not for real-time applications

5. **Request costs**
   - Lots of small requests = adds up
   - LIST operations expensive

6. **Public access risks**
   - Easy to misconfigure (make public accidentally)
   - Famous data breaches from public S3 buckets

## 8. SAP-C02 Questions Related to This

### **Question Type 1: Storage Class Selection**
```
Scenario: 500 TB data, accessed weekly for 30 days, then monthly for 1 year, then compliance archive

Answer:
- 0-30 days: S3 Standard (frequent)
- 30-365 days: S3 Standard-IA (monthly access)
- After 365 days: S3 Glacier Deep Archive (compliance, rare)

Lifecycle policy automates transitions
```

---

### **Question Type 2: Security Incident**
```
Scenario: S3 bucket was made public, confidential data exposed

Root cause: No S3 Block Public Access enabled
Solution:
- Enable S3 Block Public Access (account + bucket level)
- Use CloudFront + OAC instead of public bucket
- Audit with IAM Access Analyzer
- Monitor with CloudTrail
```

---

### **Question Type 3: Performance Optimization**
```
Scenario: Uploading 100 TB to S3, taking too long

Solutions:
- Multipart upload (parallel uploads, required for >5GB)
- Transfer Acceleration (uses CloudFront edge)
- AWS Snow family (if >10 TB and slow connection)
- Multiple prefixes (better performance distribution)

Calculation: 100 Mbps network, 100 TB = ~90 days
With Snow: 1-2 weeks including shipping
```

---

### **Question Type 4: Data Protection**
```
Scenario: Need to prevent any deletion for 7 years (compliance)

Answer: S3 Object Lock (Compliance mode)
- Cannot be deleted (even by root user!)
- Cannot be modified
- Retention period: 7 years
- Use for: SEC, FINRA, HIPAA compliance
```

---

### **Question Type 5: Cost Optimization**
```
Scenario: 80% of data not accessed after 90 days

Solution: S3 Lifecycle Policy
Transition:
- After 30 days → Standard-IA (if infrequent)
- After 90 days → Glacier Instant or Flexible
- After 7 years → Delete (if not needed)

Savings: 70-95% on old data
```

---

### **Question Type 6: Cross-Region DR**
```
Scenario: Need data in secondary region for disaster recovery

Answer: S3 Cross-Region Replication (CRR)
- Automatic replication
- Async (seconds to minutes)
- Requires versioning
- Can filter by prefix or tags
- Existing objects: Use S3 Batch Replication
```

## 9. Configurations

### **1. Bucket Creation**

```
Bucket name rules:
- Globally unique (across ALL AWS accounts!)
- 3-63 characters
- Lowercase only
- No underscores, spaces
- Must start with letter or number

Region selection:
- Choose closest to users (latency)
- Or for compliance (data residency)

Example:
Name: mycompany-prod-data-2026
Region: us-east-1
```

---

### **2. Bucket Policies (JSON)**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::mybucket/*"
    }
  ]
}

This makes bucket PUBLIC - usually DON'T do this!

Better: Use CloudFront + OAC
```

---

### **3. S3 Block Public Access (CRITICAL)**

```
Four settings (enable ALL for security):

□ BlockPublicAcls
  - Blocks setting public ACLs

□ IgnorePublicAcls  
  - Ignores existing public ACLs

□ BlockPublicPolicy
  - Blocks public bucket policies

□ RestrictPublicBuckets
  - Restricts access even if public policy exists

Best practice: Enable at account level (all buckets protected)
```

---

### **4. Versioning**

```
Enable versioning:
- Each upload creates new version
- Old versions retained
- Can retrieve/restore old versions
- Delete becomes "delete marker" (not permanent)

Example:
file.txt (Version 1) - uploaded 2026-03-01
file.txt (Version 2) - uploaded 2026-03-02  ← Current
file.txt (Version 3 - delete marker) - deleted 2026-03-03

Can restore by removing delete marker!

Cost: Pay for all versions (storage adds up)
```

---

### **5. Lifecycle Policies**

```xml
<LifecycleConfiguration>
  <Rule>
    <Status>Enabled</Status>
    <Transition>
      <Days>30</Days>
      <StorageClass>STANDARD_IA</StorageClass>
    </Transition>
    <Transition>
      <Days>90</Days>
      <StorageClass>GLACIER</StorageClass>
    </Transition>
    <Expiration>
      <Days>2555</Days> <!-- 7 years -->
    </Expiration>
  </Rule>
</LifecycleConfiguration>

Actions:
- Transition: Change storage class
- Expiration: Delete object
- Can filter by prefix, tags, size
```

---

### **6. Encryption**

**Server-Side Encryption (SSE):**

```
SSE-S3 (default):
- AWS manages keys
- AES-256
- Free
- Header: x-amz-server-side-encryption: AES256

SSE-KMS:
- You control keys via KMS
- Audit key usage (CloudTrail)
- Cost: KMS charges ($1/month per key + API calls)
- Header: x-amz-server-side-encryption: aws:kms

SSE-C (Customer-provided):
- You provide key with each request
- AWS encrypts/decrypts but doesn't store key
- You manage keys completely
```

**Client-Side Encryption:**
```
You encrypt before upload:
- AWS never sees unencrypted data
- You manage keys
- Most secure (but most complex)
```

---

### **7. Replication**

**Cross-Region Replication (CRR):**
```
Source bucket (us-east-1) → Destination bucket (eu-west-1)

Requirements:
- Versioning enabled on both
- IAM role for S3 to replicate
- Can be different accounts

What's replicated:
✅ New objects (after CRR enabled)
✅ Metadata, tags
✅ Object ACLs
✅ Delete markers (optional)

What's NOT:
❌ Existing objects (use Batch Replication)
❌ Glacier/Deep Archive objects (must restore first)
❌ Objects encrypted with SSE-C
```

**Same-Region Replication (SRR):**
```
Same as CRR but within same region

Use cases:
- Compliance (separate bucket for auditing)
- Different storage classes
- Different accounts
```

## 10. Anything Else You Need to Know

### **S3 Storage Classes - Deep Details**

**S3 Intelligent-Tiering:**
```
How it works:
- Monitors access patterns
- Moves objects between tiers automatically:
  - Frequent: Same as Standard
  - Infrequent: After 30 days no access
  - Archive: After 90 days no access
  - Deep Archive: After 180 days no access

Cost:
- Storage: Variable (depends on tier)
- Monitoring: $0.0025 per 1,000 objects

Use when: Don't know access patterns, want automatic optimization

Avoid when: Predictable patterns (manual lifecycle cheaper)
```

---

### **S3 Performance**

**Request rate limits:**
```
Per prefix:
- 3,500 PUT/COPY/POST/DELETE per second
- 5,500 GET/HEAD per second

Example:
Bucket with prefixes:
  /images/ → 5,500 GET/sec
  /videos/ → 5,500 GET/sec
  /docs/ → 5,500 GET/sec
  
Total: 16,500 GET/sec (use multiple prefixes!)
```

**Multipart Upload:**
```
For files >100 MB:
- Split into parts (5 MB - 5 GB each)
- Upload parts in parallel
- S3 assembles
- Can resume if network fails

Required for files >5 GB
Recommended for >100 MB
```

**Transfer Acceleration:**
```
Enable on bucket:
- Uses CloudFront edge locations
- Upload to edge → AWS backbone to S3
- Faster for distant users
- Cost: $0.04/GB (extra)

Example:
User in Australia uploading to us-east-1
- Direct: 300 ms latency, 10 Mbps
- Transfer Acceleration: 50 ms, 100 Mbps (10x faster!)
```

### **S3 Select and Glacier Select**

```
Problem: Download 5 GB CSV to find 10 rows
Solution: Query in S3, download only results

Example:
SELECT * FROM s3object s WHERE s.city = 'New York'

Benefits:
- Download only matching data (KB instead of GB)
- 400% faster
- 80% cheaper (less data transfer)

Limitation: Simple SQL only (no joins)
```

### **S3 Object Lock (Compliance)**

**Two modes:**

**Governance Mode:**
```
- Can't delete/overwrite
- Admin with special permission CAN override
- Use for: Internal policies
```

**Compliance Mode:**
```
- Can't delete/overwrite (NO exceptions!)
- Even root user can't delete
- Use for: SEC, HIPAA, regulatory compliance

Set retention:
- Time-based: 7 years
- Legal hold: Indefinite until removed
```

**Exam scenario:**
```
"Financial records must be kept immutable for 7 years"
→ Answer: S3 Object Lock (Compliance mode) + Glacier Deep Archive
```

Problem: Complex bucket policy for different teams

Bucket: company-data

### **Common Mistakes (Exam Traps)**

❌ **Making buckets public for CloudFront**
- Wrong: Public bucket
- Right: Private bucket + CloudFront OAC

❌ **Not enabling versioning**
- Risk: Accidental deletes permanent
- Solution: Enable versioning

❌ **Wrong storage class**
- Storing logs in Standard (expensive!)
- Use Intelligent-Tiering or lifecycle

❌ **No lifecycle policies**
- Old data in Standard (costs pile up)
- Automate transitions

❌ **Single region**
- No DR strategy
- Use Cross-Region Replication
