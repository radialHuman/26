# EC2 (Elastic Compute Cloud) - Complete Deep Dive

## 1. What Problem Did It Solve?

**Before EC2 (2006):**
- Companies bought physical servers ($5,000-50,000 each)
- Procurement took weeks/months (purchase order, shipping, data center setup)
- Over-provisioned for peak (100 servers for Black Friday, idle rest of year)
- Under-provisioned caused crashes (couldn't scale fast enough)
- Capital expense (pay upfront even if unused)
- Maintenance costs (hardware failures, upgrades)

**Problem:** Physical servers are slow, expensive, inflexible

**EC2 Solution:**
- Virtual servers in minutes (not weeks)
- Pay only for what you use (by the hour, now by the second)
- Scale up/down instantly (10 servers → 1000 servers in minutes)
- No hardware to buy/maintain
- Global deployment (launch in multiple regions)

**Impact:** Changed how companies build infrastructure - from CapEx to OpEx

## 2. What Was There Before This Service?

**Timeline:**

**1990s-2005: Physical Servers**
- Dedicated servers in company data centers
- Or colocation facilities (rent rack space)
- Manual provisioning, months to deploy

**2000-2006: Virtual Machines (VMware)**
- Virtualization on-premises
- Better utilization than physical
- Still required buying hardware

**2006: Amazon launches EC2**
- First major public cloud compute service
- Revolutionary: Rent servers by the hour
- Competitors: None initially, then Google Compute Engine (2012), Azure VMs (2010)

**Today:**
- EC2 is the foundation of AWS
- Millions of instances running globally
- Competitors: Azure VMs, Google Compute Engine, but EC2has 33% market share

## 3. When to Use It

### **Use EC2 When:**

✅ **Long-running applications**
- Web servers running 24/7
- Application servers
- Background workers

✅ **Full control needed**
- Custom OS configurations
- Specific software installations
- Root/admin access required

✅ **Stateful applications**
- Applications with persistent connections
- Session state on server
- WebSocket connections

✅ **GPU/specialized hardware**
- Machine learning training
- Video rendering
- Scientific computing

✅ **Lift-and-shift migrations**
- Moving from on-premises to cloud
- Minimal code changes

✅ **Windows applications**
- .NET Framework applications
- Windows-specific software
- Active Directory integration

### **DON'T Use EC2 When:**

❌ **Short-lived tasks (<15 minutes)**
- Use Lambda instead (serverless, cheaper)

❌ **Fully stateless HTTP APIs**
- Use Lambda + API Gateway (no server management)

❌ **Container orchestration**
- Use Fargate (serverless containers)

❌ **Unpredictable/spiky traffic**
- Lambda scales better (0 to 1000s instantly)

❌ **Simple scheduled tasks**
- Lambda with EventBridge (no always-on server)

## 4. How Is It Different from Similar Services?

### **EC2 vs Lambda**

| Feature | EC2 | Lambda |
|---------|-----|--------|
| **Server management** | You manage OS, patching | AWS manages everything |
| **Pricing** | Pay for running time (even if idle) | Pay per execution (GB-seconds) |
| **Scaling** | Manual or Auto Scaling Groups | Automatic (instant) |
| **Execution time** | Unlimited | Max 15 minutes |
| **State** | Persistent | Stateless |
| **Cold start** | None (always running) | Yes (100-500ms first request) |
| **Use case** | Long-running, stateful | Event-driven, short tasks |

**When to choose:**
- EC2: 24/7 applications, need full control
- Lambda: Event-driven, unpredictable traffic, <15 min tasks

---

### **EC2 vs ECS/Fargate**

| Feature | EC2 | ECS (EC2 launch type) | Fargate |
|---------|-----|----------------------|---------|
| **Containers** | Can run (install Docker) | Native container support | Serverless containers |
| **Management** | You manage everything | You manage EC2, AWS manages containers | AWS manages everything |
| **Orchestration** | Manual (or use Kubernetes) | Built-in (ECS) | Built-in (ECS/EKS) |
| **Use case** | Non-containerized apps | Containerized, want control | Containerized, no server management |

---

### **EC2 vs Elastic Beanstalk**

| Feature | EC2 | Elastic Beanstalk |
|---------|-----|-------------------|
| **Abstraction** | Low (you control everything) | High (AWS handles infra) |
| **Deployment** | Manual | Automated (upload code, EB deploys) |
| **Scaling** | Configure yourself | Automatic |
| **Monitoring** | Setup yourself | Built-in |
| **Use case** | Full control needed | Quick app deployment, PaaS |

## 5. Underlying Mechanism and How It's Made

### **Technical Architecture:**

**What EC2 Actually Is:**

1. **Hypervisor Technology:**
   - AWS uses **Nitro Hypervisor** (custom-built)
   - Replaces older Xen hypervisor
   - Virtualizes hardware (CPU, memory, storage, network)
   
2. **Physical Infrastructure:**
   ```
   AWS Data Center
     └─ Racks of physical servers
         └─ Each server runs Nitro Hypervisor
             └─ Multiple EC2 instances per server
                 └─ Your instance (isolated from others)
   ```

3. **Isolation:**
   - Hardware virtualization (not containers)
   - Strong isolation between customers
   - Dedicated CPU/memory/storage per instance
   - Cannot see other customers' instances

4. **Nitro System Components:**
   - **Nitro Cards:** Offload networking, storage, security
   - **Nitro Hypervisor:** Lightweight virtualization
   - **Nitro Security Chip:** Hardware-based security
   
   **Benefit:** Near bare-metal performance

---

### **Instance Lifecycle:**

```
Launch Instance
  ↓
AWS allocates:
  - Physical server with capacity
  - Virtual CPU cores
  - Memory
  - Network interface
  - EBS volume (if not instance store)
  ↓
Boot process:
  - Load AMI (operating system image)
  - Start OS
  - Run user data script (if provided)
  ↓
Running state:
  - You can connect (SSH/RDP)
  - Application runs
  - Billed by the second
  ↓
Stop (EBS-backed):
  - OS shuts down
  - RAM cleared
  - EBS volumes persist
  - No compute charges (still pay for EBS)
  - Can start again later
  ↓
Terminate:
  - Instance deleted
  - Root EBS deleted (by default)
  - Gone forever
```

---

### **How Placement Works:**

```
Region (e.g., us-east-1)
  └─ Availability Zone A
      └─ Data Center 1
          └─ Rack 1
              └─ Physical Server A
                  └─ Your EC2 instance
                  
AWS decides placement based on:
- Availability
- Capacity
- Placement group rules (if specified)
```

## 6. Cost

### **Pricing Models:**

**1. On-Demand (Pay-As-You-Go)**
```
Price: $0.0464/hour for t3.medium (example)
Billing: Per second (60-second minimum)
Use when: Unpredictable workloads, short-term, testing

Example monthly cost:
t3.medium 24/7: $0.0464 × 730 hours = $33.87/month
```

**2. Reserved Instances**
```
Commitment: 1 or 3 years
Discount: Up to 72% vs On-Demand

t3.medium pricing:
- On-Demand: $33.87/month
- Reserved (3-year, all upfront): $9.42/month (72% savings)

Types:
- Standard RI: Can't change instance family (locked to t3)
- Convertible RI: Can change to different family (less discount, ~54%)
```

**3. Savings Plans**
```
Commitment: $/hour for 1 or 3 years
Flexibility: Can change instance family, size, OS, region
Discount: Up to 72%

Example:
Commit to $20/hour for 3 years
Use across: t3.large in us-east-1, then switch to m5.xlarge in eu-west-1
```

**4. Spot Instances**
```
Discount: Up to 90% vs On-Demand
Risk: AWS can terminate with 2-minute warning
Price: Varies based on supply/demand

t3.medium:
- On-Demand: $0.0464/hour
- Spot (typical): $0.0139/hour (70% savings)
- Spot (best): $0.0046/hour (90% savings)

Use for: Batch jobs, fault-tolerant workloads, CI/CD
```

**5. Dedicated Hosts**
```
Price: $1.176/hour for m5 Dedicated Host (example)
What you get: Entire physical server
Use for: Licensing (BYOL), compliance, dedicated hardware

Cost: Much higher than shared instances
```

**6. Dedicated Instances**
```
Price: On-Demand + $2/hour per region dedicated instance fee
What you get: Instance on hardware dedicated to you (but not full host control)
```

---

### **Additional Costs:**

**Data Transfer:**
- IN: Free
- OUT to internet: $0.09/GB (first 10 TB)
- Between regions: $0.02/GB
- Within same AZ: Free

**EBS Volumes:**
- gp3: $0.08/GB/month
- io2: $0.125/GB/month + IOPS charges

**Elastic IPs:**
- Free while attached to running instance
- $0.005/hour if not attached (to prevent waste)

## 7. Pros and Cons

### **Pros ✅**

1. **Flexibility**
   - Any OS (Linux, Windows, custom)
   - Any software
   - Root access
   
2. **Wide Range of Instance Types**
   - General purpose, compute-optimized, memory-optimized, storage-optimized, GPU
   - 500+ instance type combinations
   
3. **Pricing Options**
   - On-Demand, Reserved, Spot, Savings Plans
   - Choose based on workload

4. **Integration**
   - Works with all AWS services
   - VPC, IAM, CloudWatch, etc.

5. **Proven and Mature**
   - 18+ years in production
   - Battle-tested
   - Extensive documentation

6. **Global**
   - 30+ regions
   - Deploy close to users

### **Cons ❌**

1. **Management Overhead**
   - You manage OS updates
   - Security patching
   - Monitoring
   - Scaling configuration

2. **Always Running = Always Paying**
   - Idle instance still costs money
   - Need to stop/terminate when not needed

3. **Scaling Not Instant**
   - Launch takes 30-60 seconds
   - Not as fast as Lambda (instant)

4. **Complexity**
   - Many options to configure
   - Easy to misconfigure
   - Steep learning curve

5. **Cost Can Get High**
   - Forgot to stop instances = big bill
   - Data transfer costs add up
   - Need active cost management

## 10. Anything Else You Need to Know

### **Instance Families - Deep Dive**

**T family (Burstable):**
- CPU Credits system
- Baseline performance (e.g., 20% CPU)
- Can burst to 100% using credits
- Credits regenerate over time
- If out of credits: Throttled to baseline
- Use for: Variable workload (web servers with occasional spikes)
- **Trap:** Credits run out → performance tanks

**M family (General Purpose):**
- Balanced CPU/memory
- Consistent performance
- No credit system
- Use for: Most applications

**C family (Compute-Optimized):**
- High CPU, less memory
- Use for: Batch processing, encoding, gaming servers, scientific modeling

**R family (Memory-Optimized):**
- High memory, less CPU
- Use for: In-memory databases (Redis, SAP HANA), big data processing

**I/D family (Storage-Optimized):**
- High disk throughput/IOPS
- Use for: NoSQL databases, data warehousing, Elasticsearch

**P/G family (GPU):**
- GPU acceleration
- P: High-performance (ML training)
- G: Graphics (rendering, gaming)

---

### **Instance Store vs EBS**

**Instance Store:**
- Physically attached to host server
- Ephemeral (lost on stop/terminate)
- Highest performance (NVMe SSD)
- Free (included in instance price)
- Use for: Temporary data, caches, buffers

**EBS:**
- Network-attached storage
- Persistent (survives stop/terminate if configured)
- Can detach and reattach
- Snapshot for backup
- Costs extra
- Use for: Database, application data

---

### **Auto Scaling Concepts**

**Auto Scaling Group (ASG):**
```
Components:
- Launch Template (what to launch)
- Min/Desired/Max capacity (2/5/10 instances)
- Scaling policies (when to scale)
- Health checks (replace unhealthy)

Scaling Policies:
1. Target Tracking: "Keep CPU at 70%"
2. Step Scaling: "Add 2 when CPU > 80%, add 5 when > 90%"
3. Scheduled: "10 instances at 9AM, 2 at 6PM"
4. Predictive: ML-based forecasting
```

---

### **Placement Groups**

**Cluster:**
- All instances in same rack
- Lowest latency (same network switch)
- Use for: HPC, big data
- Risk: Rack failure affects all

**Spread:**
- Each instance on different hardware
- Max 7 instances per AZ
- Use for: Critical instances (avoid correlated failures)

**Partition:**
- Groups of instances on separate hardware
- Up to 7 partitions per AZ
- Use for: Distributed systems (Kafka, HDFS)

---

### **Hibernation**

```
Stop vs Hibernate:

Stop:
- RAM cleared
- Boot from scratch (30-60 sec)

Hibernate:
- RAM saved to EBS root volume
- Resume with same state (faster boot)
- Must enable at launch
- RAM must fit on EBS volume
```

Connect via browser (no SSH key needed):

- Alternative to bastion hosts

### **Common Mistakes**

❌ **Leaving instances running when not needed**
- Solution: Stop when not in use, use Lambda for event-driven

❌ **Wrong instance type**
- Solution: Use Compute Optimizer recommendations

❌ **No backups**
- Solution: EBS snapshots, AMIs

❌ **Single AZ**
- Solution: Use Auto Scaling across multiple AZs

❌ **Hardcoded credentials**
- Solution: Use IAM roles

❌ **No monitoring**
- Solution: Enable CloudWatch detailed monitoring

---

### **Best Practices**

✅ **Use IAM roles** (not access keys)
✅ **Enable detailed monitoring** for production
✅ **Use Auto Scaling** (even for single instance - auto-recovery)
✅ **Multi-AZ deployment** for high availability
✅ **Tag everything** (for cost allocation)
✅ **Use latest generation** instances (better performance/cost)
✅ **Right-size** instances (use Compute Optimizer)
✅ **Use Systems Manager** instead of SSH (better security)
✅ **Enable termination protection** for critical instances
✅ **Encrypt EBS volumes** (security/compliance)
