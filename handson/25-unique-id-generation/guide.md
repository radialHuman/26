# Unique ID Generation

## What it is
Generating IDs that are globally unique across distributed servers, without requiring a central coordinator to assign them, ideally sortable by time.

## Why it matters
Every record needs an ID. Auto-increment from a single DB doesn't scale horizontally (multiple DBs would conflict). UUID v4 is random — you can't sort by it to get chronological order. Twitter's Snowflake ID solves both: unique, distributed, and time-sortable. Interviewers ask this when you say "we'll use auto-increment IDs" in any sharded system.

## What to know before starting
- Why auto-increment breaks across multiple DB shards (shard 1 generates ID=1, shard 2 also generates ID=1)
- What a UUID is: 128-bit random number, globally unique but not time-sortable
- Binary representation: a 64-bit integer has room for timestamp + machine ID + sequence

## How to approach it
**Snowflake structure** (Twitter's approach):
```
[1 bit sign][41 bits timestamp ms][10 bits machine ID][12 bits sequence]
```
- 41 bits of millisecond timestamp = ~69 years
- 10 bits machine ID = 1024 unique generators
- 12 bits sequence = 4096 IDs per millisecond per machine

When the sequence overflows within a millisecond, wait for the next millisecond.

This gives you: unique (no coordination needed), sortable by time (leading bits are timestamp), 64-bit integer (fits in standard DB columns).

## What to build (minimal working version)
- `SnowflakeGenerator(machine_id)` class
- `generate()` method: get current ms timestamp, combine with machine_id and incrementing sequence
- Handle sequence overflow: if 4096 IDs generated in one ms, wait for next ms
- Run 3 generators with different machine_ids simultaneously; generate 10,000 IDs; confirm no collisions
- Confirm IDs are sortable (sort them; verify they're in time order)

## Knobs to turn
- Run two generators with the same machine_id. Generate 1M IDs. Find collisions.
- Set the clock back (simulate clock skew). What happens to ID generation? (A serious failure mode)
- Compare UUID v4 sort order vs. Snowflake sort order when used as DB primary keys. Impact on index performance?
- Implement UUID v7 (time-ordered UUID): simpler than Snowflake, no machine ID needed.

## How it connects to other components
- `49-sharding` — Snowflake IDs can be used as shard keys (time-sortable, no hotspot)
- `13-idempotency` — idempotency keys are often Snowflake or UUID IDs generated by the client

## Real tool / production system
Twitter Snowflake (open source). Instagram used a variant with Postgres. Discord uses their own Snowflake variant. MongoDB ObjectID is a similar concept. UUID v7 (RFC 9562) is the newer standard. What you're missing: clock skew handling (NTP correction, reject backwards clock), machine ID assignment coordination, and monotonicity guarantees.
